Unit 3: Object Oriented Analysis, Design & Programming Style

This module provides an exhaustive architectural synthesis of software design methodologies, exploring Rumbaugh's three-model integration, design optimization algorithms, procedural C object emulation, and system quality attributes.

1. Stages of Object-Oriented Design (OOD)

Object-Oriented Design (OOD) transforms the conceptual models formulated during Object-Oriented Analysis (OOA) into an executable computational blueprint. OOD proceeds in two rigorous, distinct stages:

Design Stage Architectural Focus Critical Technical Decisions
System Design (Macro Level) High-level strategic architecture, system partitioning, and infrastructure mapping.
  • Subsystem Decomposition: Partitioning software into autonomous, loosely coupled subsystems (e.g., UI, Core Domain, Payment, Notification).
  • Hardware-Software Allocation: Mapping software subsystems to physical server nodes and devices.
  • Concurrency Strategy: Identifying concurrent threads, processes, thread pools, and asynchronous event queues.
  • Data Store Management: Choosing relational SQL, distributed NoSQL document stores, or in-memory caches.
  • Global Resource Control: Enforcing access protocols (mutexes, distributed locks) for shared physical resources.
  • Boundary Conditions: Establishing initialization, system boot, failover recovery, and clean shutdown policies.
Object Design (Micro Level) Detailed internal specification of individual classes, algorithms, and data structures.
  • Algorithm Selection: Choosing concrete computational algorithms (sorting, searching, route optimization) for each operation.
  • Data Structure Selection: Mapping abstract associations into concrete arrays, balanced binary trees, or hash maps.
  • Design Optimization: Introducing redundant lookup links, caching derived attributes, and adjusting class hierarchies.
  • Visibility Enforcement: Assigning strict private, protected, and public access controls.
  • Implementation of Control: Selecting between procedure-driven control (call-return) or event-driven state engines.

2. Combining the Three Models (Rumbaugh's OMT)

James Rumbaugh formulated the Object Modeling Technique (OMT) on the foundational axiom that a software system cannot be understood through a single paradigm. OMT synthesizes three orthogonal modeling views:

Figure 3.1: The Tripartite Model Integration of Rumbaugh's OMT

The Integration Mechanism

  1. Object Model provides the Foundation: Identifies the state variables and memory structures upon which operations act.
  2. Dynamic Model drives Execution Flow: Defines when operations execute in response to incoming events and state transitions. Events in the dynamic model become operation invocations in the object model.
  3. Functional Model defines Computational Logic: Specifies how data values are transformed mathematically. Processes in the DFD become method bodies in the object model.

3. Design Optimization Strategies

Analysis models emphasize real-world domain fidelity without regard for physical execution constraints. During Object Design, the engineer refactors the design to optimize throughput, latency, and memory footprint:

1. Adding Redundant Associative Paths

Navigating deep association chains (e.g., Company → Division → Department → Team → Employee) has high time complexity ($O(N)$). When queries frequently traverse from Company directly to Employee, the designer adds a cached direct associative pointer from Company directly to Employee, converting deep lookups to $O(1)$.

2. Rearranging Execution Paths & Predicate Ordering

When filtering collections with compound boolean conditions (conditionA && conditionB), reorder predicates so the most selective, computationally inexpensive filter evaluates first. This triggers early short-circuit evaluation, skipping heavy downstream checks.

3. Caching Derived Attributes

In high-throughput systems, recalculating complex derived values on-the-fly (e.g., an e-commerce cart total or customer credit rating) causes massive CPU overhead. If read queries significantly exceed write updates, the computed value is cached in a private attribute and recomputed only on state mutations.

4. Inheritance Adjustment

During detailed design, class hierarchies are adjusted to balance maintainability and performance:

  • Factoring Common Behavior: When disparate subclasses share identical attributes or methods, factor them upward into a newly introduced abstract superclass.
  • Flattening Redundant Superclasses: When intermediate abstract classes introduce trivial layers of indirection without behavioral variation, collapse them into the derived classes to eliminate VTable dispatch overhead.
  • Delegation over Inheritance: When inheritance is misused purely for partial code reuse (violating Liskov Substitution Principle), replace inheritance with object composition (delegation).

5. Physical Packaging & Documentation Design

Physical Packaging & Compilation Firewalls

  • Header Separation: Strict separation of public declarations in .hpp files from private implementations in .cpp compilation units.
  • Forward Declarations: Replace heavy #include directives with forward declarations (e.g., class Order;) in header files to eliminate circular dependencies and minimize recompilation cascades.
  • The PIMPL Idiom (Pointer to Implementation): Hiding a class's private members inside an opaque pointer to an internal struct, completely decoupling client binaries from private layout changes.

Documentation: Design by Contract (Bertrand Meyer)

Robust object-oriented systems enforce formal contracts specifying:

  • Preconditions: Invariants the caller must satisfy before invoking a method (e.g., amount > 0.0).
  • Postconditions: Invariants the method guarantees upon successful completion (e.g., balance_new == balance_old - amount).
  • Class Invariants: Invariants that must hold true throughout the entire lifetime of the object.

6. Methodological Comparisons: SA/SD vs. JSD vs. OOAD

Criteria SA/SD (Structured) JSD (Jackson Structured Development) OOAD (Object-Oriented)
Originators Yourdon, DeMarco, Constantine Michael A. Jackson Booch, Rumbaugh, Jacobson
Core Philosophy Top-down functional decomposition; systems are pipelines transforming data flows. Real-world modeling based on time-ordered event histories experienced by domain entities. Domain decomposition; autonomous objects communicating via message-passing contracts.
Primary Artifacts Data Flow Diagrams (DFDs), Structure Charts, Data Dictionaries. Entity Structure Diagrams (ESDs), System Specification Diagrams (SSDs). Class Diagrams, Statecharts, Sequence Diagrams, Component Diagrams.
Strengths Intuitive for algorithmic batch transformations and compilers. Superior modeling of concurrent, time-ordered entity lifecycles. Unmatched modularity, code reuse, resilience, and real-world domain fidelity.
Weaknesses Fragile against data modifications; large analysis-to-design semantic gap. Difficult to map onto standard procedural programming languages. Steeper learning curve; requires significant upfront architectural modeling.

7. Complete C Procedural OOP Emulation

Object orientation is an architectural discipline, not a syntax feature. Even in procedural C, OOP concepts (Classes, Encapsulation, Single Inheritance, and Dynamic Polymorphism) can be implemented directly using structs, function pointers, and VTables:

/* =========================================================================
   COMPLETE OBJECT-ORIENTED ENGINE IMPLEMENTED IN STANDARD PROCEDURAL C
   Demonstrating Classes, Encapsulation, Single Inheritance & VTable Dispatch
   ========================================================================= */
#include <stdio.h>
#include <stdlib.h>

// Forward declaration of VTable
struct ShapeVTable;

// Base Class: Shape
typedef struct Shape {
    const struct ShapeVTable* vptr; // Virtual Method Table Pointer
    double x, y;                    // Base Attributes
} Shape;

// Shape VTable Contract
typedef struct ShapeVTable {
    double (*area)(const Shape* self);
    void (*draw)(const Shape* self);
} ShapeVTable;

// Derived Class: Circle
typedef struct Circle {
    Shape base;      // Inheritance: Base class embedded at byte offset 0!
    double radius;   // Derived attribute
} Circle;

// Circle Member Method Implementations
double Circle_area(const Shape* self) {
    const Circle* c = (const Circle*)self; // Safe downcast due to offset 0
    return 3.14159265 * c->radius * c->radius;
}

void Circle_draw(const Shape* self) {
    const Circle* c = (const Circle*)self;
    printf("[Circle]: Drawing at (%.1f, %.1f) with radius %.2f | Area = %.2f\n", 
           self->x, self->y, c->radius, Circle_area(self));
}

// Static VTable for Circle
static const ShapeVTable circle_vtable = {
    Circle_area,
    Circle_draw
};

// Circle Constructor
Circle* Circle_create(double x, double y, double r) {
    Circle* c = (Circle*)malloc(sizeof(Circle));
    c->base.vptr = &circle_vtable; // Initialize VPTR to Circle VTable
    c->base.x = x;
    c->base.y = y;
    c->radius = r;
    return c;
}

// Generic Polymorphic Dispatch Function
void renderShape(const Shape* s) {
    s->vptr->draw(s); // Dynamic dispatch via VTable!
}

int main() {
    Circle* c = Circle_create(10.0, 20.0, 5.0);
    renderShape((Shape*)c); // Polymorphic call in C!
    free(c);
    return 0;
}

8. Core Software Engineering Quality Attributes

Quality Dimension Formal Definition Object-Oriented Architectural Enforcement
Robustness The capability of a software system to withstand exceptional errors, invalid user inputs, and unexpected hardware failures without crashing.
  • Class invariant validation in constructors and setters.
  • Type-safe C++ exception hierarchies (std::exception).
  • RAII (Resource Acquisition Is Initialization) ensuring deterministic memory cleanup.
Extensibility The ease with which a system accommodates new functional capabilities without altering or destabilizing existing source code.
  • Adherence to the Open-Closed Principle (OCP).
  • Polymorphic dynamic dispatch through abstract base interfaces.
  • Pluggable architecture patterns (Strategy, Factory, Observer).
Reusability The extent to which existing software modules can be utilized across new applications with zero or minimal modification.
  • Composition over inheritance ("has-a" over "is-a").
  • Generic template libraries (C++ STL containers and algorithms).
  • Autonomous package encapsulation with minimal dependencies.
