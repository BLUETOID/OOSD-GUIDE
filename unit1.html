Unit 1: Introduction to Object Orientation & UML

This module covers the complete Unit 1 syllabus: Object-Oriented fundamentals, the principles and goals of modeling, a complete introduction to UML, the Conceptual Model of UML (Building Blocks, Rules, Common Mechanisms), and UML Architecture (4+1 View Model and OMG Metamodeling).

1. The Object-Oriented Paradigm

Object-Oriented Technology (OOT) structures software as autonomous entities called objects, encapsulating data attributes and member operations. Unlike procedural programming where global data structures are manipulated by detached procedures, OOT bounds data mutation strictly within class interfaces.

Why Object Orientation? (The Software Crisis)

During the early decades of computing, procedural and structured programming (Fortran, Pascal, C) suffered fundamental failures when systems scaled to large commercial applications:

  • Global Data Vulnerability: Procedural architecture enforces a dichotomy between active subroutines and passive data structures. As systems expanded, data was placed in global scopes, allowing any function to arbitrarily mutate shared memory without validation, leading to state corruption.
  • Ripple Effects: Functions are tightly coupled to the physical layout of data records. Adding a single field to a struct required editing every procedure across hundreds of files that referenced it.
  • Semantic Gap: Real-world systems consist of tangible entities (bank accounts, patients, aircraft) that maintain internal state and collaborate through communications. Procedural decomposition into artificial functional flowcharts created a severe cognitive gap between domain and software.

The Object-Oriented Paradigm resolves this by establishing the Object as the foundational building block. An OO system is organized as a dynamic, decentralized society of autonomous, collaborating entities. Each object encapsulates both state (private instance variables) and behavior (public operations). Computation proceeds via message passing: client objects invoke operations on server objects without knowledge of internal implementation.

Facet Procedural Paradigm (C) Object-Oriented Paradigm (C++)
Primary Decomposition Functional Decomposition (algorithms, step-by-step routines). Object Decomposition (autonomous domain entities).
Data & Logic Relationship Separated: Data structures are passive, passed into external functions. Cohesive: Data and functions are packaged inside the class boundary.
Access Control Weak or absent: All struct members are public; global variables modifiable anywhere. Strict: Access specifiers (private, protected, public) enforce information hiding.
Code Reuse Copy-pasting or static library functions. Inheritance, object composition, polymorphism, and generic templates.
Modification Impact High ripple effect across dependent procedural files. Localized within the class boundary; external callers interact via stable contracts.

Code Demonstration: Procedural vs. OOP

// Encapsulation: Private state protected by public methods
class BankAccount {
private:
    double balance; // Private data
public:
    void deposit(double amount) { balance += amount; }
    double getBalance() const { return balance; } // Public contract
};

2. Core Object-Oriented Concepts

2.1 Object Identity

Definition: Object identity is the property of an object which distinguishes it from all other objects, regardless of its state values, data types, or variable references.

Identity vs. Equality

  • Equality (State Match): Two distinct objects are equal if their internal attribute values evaluate to identical values. Example: two separate customer records for "John Doe" born on "1990-01-01" have identical state.
  • Identity (Sameness): Objects are identical strictly if they are the exact same physical instance at the same memory address. Even if two objects share identical data, they remain non-identical entities.
// Object Identity vs Equality
Student s1(101, "Alice");
Student s2(101, "Alice"); // s1.equals(s2) is TRUE, but &s1 != &s2 (distinct identity)

Physical Realization of Identity

  • In-Memory (Runtime): Enforced via hardware pointer addresses (the hidden this pointer passed automatically to member operations).
  • Persistent Storage: In databases where memory addresses are transient, identity is preserved using surrogate primary keys (UUIDs or auto-incrementing integers).

2.2 Encapsulation & Information Hiding

While often used interchangeably, these represent distinct concepts:

  • Encapsulation: The programming language mechanism that packages data variables and member operations into a single syntactic unit (the class).
  • Information Hiding (Parnas Principle): The design strategy of intentionally concealing internal data representations and algorithmic mechanisms behind a public abstract interface.
Figure 1.1: Encapsulation Boundary and Information Hiding Contract

Benefits of Encapsulation

  1. Class Invariant Defense: An invariant is a condition that must hold true for an object to remain valid (e.g., balance >= 0). By preventing direct variable access, setter methods validate all incoming parameters.
  2. Implementation Independence: Internal data structures can be refactored (e.g., replacing a vector with a hash map) without altering or recompiling client code.

2.3 Polymorphism

Definition: Polymorphism ("many forms") is the capability of a single message invocation to exhibit diverse behaviors depending on the dynamic type of the receiver object.

Type Mechanism Binding Time Example
Static (Compile-Time) Function Overloading, Operator Overloading, Templates Early Binding (Compilation) void print(int); void print(string);
Dynamic (Runtime) Inheritance with virtual member functions Late Binding (Execution) Shape* s = new Circle(); s->draw();

Dynamic Dispatch: VTable Mechanism

When a C++ compiler encounters a class with at least one virtual function:

  1. VTable Generation: The compiler builds a static array of function pointers (the Virtual Method Table) for that class. Each slot stores the address of a virtual function.
  2. VPTR Insertion: A hidden pointer (vptr) is injected into every object instance, pointing to the class's VTable.
  3. Dynamic Resolution: When basePtr->virtualMethod() is called, machine code dereferences vptr, indexes into the VTable slot, and jumps to the resolved function address.
Figure 1.2: Physical Memory Architecture of Dynamic Dispatch (VPTR and VTable)
class Vehicle {
public:
    virtual void ignite() = 0; // Pure abstraction (interface contract)
};
class ElectricCar : public Vehicle {
public:
    void ignite() override { /* Inverter activation */ } // Polymorphic dispatch
};

2.4 Generosity (Genericity / Generic Programming)

Definition: Generosity (genericity) is the technique of constructing classes and algorithms parameterized by data types, enabling maximum code reuse without binding to a specific concrete type at authoring time.

// Genericity (Generosity): Parameterized type abstraction
template <typename T>
class Stack {
    T elements[100];
    int top = -1;
public:
    void push(const T& item) { elements[++top] = item; }
    T pop() { return elements[top--]; }
};

3. Principles & Goals of Modeling

A model is a semantically closed, purposeful simplification of reality. In software engineering, constructing a model is the fundamental medium through which systems are conceived, explored, analyzed, and verified before committing expensive development resources.

The Five Strategic Goals of Software Modeling

  1. Visualizing the System: Complex software spans millions of lines where structural patterns are obscured in flat text files. Visual modeling allows architects to view the ecosystem at varying granularities, identifying dependencies, bottlenecks, and coupling anti-patterns instantly.
  2. Specifying Structure and Behavior: Natural language specifications are inherently ambiguous. Visual models provide standardized graphical syntax and formal semantic constraints that define exact interface contracts, attribute types, and operational preconditions.
  3. Providing a Construction Template: High-integrity models serve as the direct blueprint from which classes, database schemas, and API endpoints are generated. Modern CASE tools perform forward engineering to generate code directly from class models.
  4. Documenting Decisions and Design Rationale: Over decades of system evolution, original architects leave organizations. Models document why specific trade-offs were selected, preserving architectural memory.
  5. Early Risk Mitigation: Identifying an architectural flaw during modeling costs roughly 1% of the expenditure required after deployment.

The Four Fundamental Principles of Modeling (Booch, Rumbaugh, Jacobson)

  1. Principle 1 — The Choice of Model Shapes the Solution:

    The choice of modeling paradigm dictates the architecture. If one chooses procedural models (DFDs), the solution crystallizes around sequential transformations. If one chooses object-oriented models (UML), the system emerges as an ecosystem of autonomous, collaborating entities.

  2. Principle 2 — Every Model May Be Expressed at Different Levels of Precision:

    A system must be modelable at multiple granularities. Early in requirements, architects construct high-level elided models (class names only) for stakeholder communication. Later, the same model is refined with typed method signatures, parameter semantics, and pre/post-conditions.

  3. Principle 3 — The Best Models Are Connected to Reality:

    Models must account for hardware topologies, network limits, database isolation guarantees, and programming language constructs. When business domain changes occur, modifications must map directly and traceably to the model and code.

  4. Principle 4 — No Single Model Is Sufficient:

    A complex system cannot be captured in a single diagram. High-integrity engineering requires decomposing the model into multiple complementary, orthogonal viewpoints (static structural, behavioral interaction, physical deployment) — as captured by the 4+1 view architecture.

4. Introduction to UML: History, Foundations & Standards

The Unified Modeling Language (UML) is the international industry-standard visual modeling language ratified by the Object Management Group (OMG) for specifying, visualizing, constructing, and documenting the artifacts of software-intensive systems.

4.1 The Historical Evolution: Resolving the "Method Wars"

In the late 1980s and early 1990s, the software industry experienced the chaotic era known as the "Method Wars". Over fifty competing, proprietary object-oriented analysis and design methodologies existed simultaneously, each with its own idiosyncratic notation, semantics, and terminology:

  • The Booch Method (Grady Booch): Focused on detailed OO design and static structural relationships. Used distinctive "cloud" notation for classes.
  • Object Modeling Technique — OMT (James Rumbaugh): Emphasized rigorous structural data analysis, dynamic state modeling, and functional decomposition for data-intensive commercial systems.
  • Objectory (Ivar Jacobson): Pioneered the Use Case approach, placing user scenarios and external business actors at the center of requirements engineering.

This fragmentation severely damaged the industry — organizations could not share visual models, CASE tool vendors were paralyzed, and developers faced immense retraining costs.

4.2 The "Three Amigos" & OMG Standardization

In 1994, James Rumbaugh joined Grady Booch at Rational Software Corporation to unify their methods. In 1995, Ivar Jacobson joined following Rational's acquisition of Objectory AB. Together, they became the "Three Amigos", synthesizing the best elements of their respective methodologies into a unified visual grammar.

Figure 1.3: Evolution of UML from the Three Methodologies

In 1997, the OMG formally adopted UML 1.1. Subsequent evolutions culminated in UML 2.0 (2005) and UML 2.5 (current), expanding the diagram taxonomy from 9 to 14 distinct diagrams and adding interaction frames, structured component ports, and formalized activity token flow.

4.3 What UML Is and What It Is NOT

What UML IS What UML IS NOT
A standardized visual modeling language with formal metamodel semantics. NOT a programming language (it produces visual blueprints, not compiled bytecode).
Applicable across any programming language (C++, Java, C#, Python). NOT proprietary or tied to any single software vendor or OS.
Methodology-agnostic: Usable in Agile, Scrum, Unified Process, or Waterfall. NOT a prescriptive software lifecycle process or methodology.
A visual communication medium bridging business analysts and system architects. NOT a flowcharting tool for trivial procedural scripts.

5. Conceptual Model of UML: The Three Pillars

To master UML, one must understand its Conceptual Model. This model is structured upon three foundational pillars that define the grammar, vocabulary, and assembly rules of the language:

  1. Building Blocks: The core modeling elements — Things, Relationships, and Diagrams.
  2. Rules of UML: Syntactic and semantic well-formedness constraints governing how building blocks can be legally assembled.
  3. Common Mechanisms: Universal structural patterns and extensibility features applied consistently across all UML diagrams.

6. Building Blocks of UML (Deep Dive)

6.1 Things in UML — The Four Categories

Things are the fundamental modeling elements, the nouns and verbs of the UML vocabulary. They are classified into four categories:

Category Elements Meaning, Notation & Role
1. Structural Things
(Static blocks)		 Class, Interface, Collaboration, Use Case, Active Class, Component, Node, Artifact The physical and conceptual nouns of a model.
• Class: 3-compartment rectangle (Name | Attributes | Operations). Defines state and behavioral contract. Most important structural thing.
• Interface: Named circle ("lollipop") or rectangle stereotyped with «interface». Specifies operations with zero implementation.
• Collaboration: Dashed ellipse representing a society of cooperating roles fulfilling a use case or design pattern.
• Use Case: Solid horizontal ellipse enclosing an action phrase. An observable unit of functionality delivered to an external actor.
• Active Class: Rectangle with double vertical border lines. Represents a class owning a concurrent execution thread.
• Component: Modular packaging unit with tabs or component icon representing physical software code (JAR, DLL, executable).
• Node: 3D cuboid representing a physical hardware resource (server, sensor, mobile device) with memory and processing capacity.
• Artifact: Physical file on a node (SQL script, binary, config YAML).
2. Behavioral Things
(Dynamic blocks)		 Interaction (Message), State Machine, Activity The verbs of a model, representing dynamic behavior over time.
• Interaction: A set of messages exchanged among objects within a context to achieve a purpose. Represented by directed arrows with sequence numbers and method signatures.
• State Machine: Specifies the sequence of states an object traverses during its lifecycle in response to events. Represented by rounded rectangles (states) and directed arrows (transitions).
• Activity: Specifies the computational workflow of operations involving actions and token flows.
3. Grouping Things
(Organizational blocks)		 Package The organizational mechanism to decompose complex models into modular subsystems.
• Package: Tabbed folder icon. Can enclose structural things, use cases, or nested packages to define namespace boundaries, access visibilities, and deployment units.
4. Annotational Things
(Explanatory blocks)		 Note (Comment) The explanatory elements of a model.
• Note: A dog-eared rectangle connected via a dashed line. Used to express design rationale, constraints, requirements, or comments.

6.2 Relationships in UML

Things do not exist in isolation; they are bound together through four fundamental semantic relationships:

Relationship Notation Meaning & Usage
Dependency Dashed line with open arrowhead (client → supplier) A semantic relationship where a change to the supplier may affect the client. Example: A Report class depends on a DatabaseConnection for data retrieval.
Association Solid line adorned with role names, navigation arrows, and multiplicities A structural relationship describing a set of links connecting object instances. Includes two specialized forms:
• Aggregation: Shared "has-a" (hollow diamond ◇ at whole end). Parts can exist independently.
• Composition: Strict "owns-a" (filled diamond ◆ at whole end). Parts have coincident lifetimes with the whole.
Generalization Solid line with hollow triangular arrowhead (child → parent) Taxonomic "is-a" relationship. The child inherits all attributes, operations, and relationships of the parent. Example: SavingsAccount generalizes Account.
Realization Dashed line with hollow triangular arrowhead One classifier specifies a contract (interface) and another guarantees to fulfill it. Example: PayPalGateway realizes «interface» PaymentProcessor.
Figure 1.6: Visual Notation of All UML Relationships

7. Rules of the UML & Common Mechanisms

Pillar 2: Rules of the UML (Semantic Well-Formedness)

UML building blocks cannot be combined haphazardly. The OMG specification establishes five categories of semantic rules:

  • Names: Every element must possess a legal textual identifier conforming to namespace uniqueness rules. A name cannot collide with peer elements within the same enclosing namespace.
  • Scope: Defines the bounding context that owns and encloses a name. A class Account inside package CorporateBanking does not conflict with Account inside RetailBanking. Fully qualified syntax: PackageName::ElementName.
  • Visibility: Dictates access from outside the declaring container. UML standardizes four visibility levels:
    • + Public: Globally accessible by any classifier.
    • - Private: Accessible only within the declaring classifier; hidden from subclasses and external clients.
    • # Protected: Accessible within the declaring classifier and its derived subclasses.
    • ~ Package: Accessible only to classifiers within the same enclosing package.
  • Integrity: Rules governing how elements legally connect. For example: an interface cannot inherit from a concrete class; an association cannot terminate on a note; an abstract class cannot be instantiated directly.
  • Execution: Dynamic semantics defining execution causality (run-to-completion for state transitions, token flow in activity diagrams, message ordering in sequence lifelines).

Pillar 3: Common Mechanisms of the UML

UML achieves simplicity and consistency by applying four common mechanisms across all diagram types:

  1. Specifications: Behind every visual symbol lies a comprehensive textual specification containing full typing rules, constraints, and semantics. The visual icon is merely the graphical projection of this deeper specification.
  2. Adornments: Every element has a basic notation that can be embellished with textual details (multiplicity 0..*, navigation arrows, abstract italicization, stereotypes).
  3. Common Divisions:
    • Class vs. Object: Abstract type classifier (e.g., Account) vs. runtime instance (e.g., acc1 : Account).
    • Interface vs. Implementation: Public behavioral contracts (what) vs. private algorithmic realization (how).
    • Type vs. Role: What an entity fundamentally is (static type) vs. the contextual hat it wears during a collaboration (role name).
  4. Extensibility Mechanisms (The Extensibility Trio): Allows UML to be tailored to specialized domains without altering the foundational metamodel:
    • Stereotypes («stereotype»): Extends the vocabulary by introducing new domain-specific elements based on existing classifiers. Example: «entity», «service», «thread».
    • Tagged Values ({tag = value}): Extends properties with arbitrary metadata. Example: {version = 2.4, author = "SecurityLead"}.
    • Constraints ({boolean expression}): Enforces invariant conditions. Example: {balance >= 0}, {ordered}, {frozen}.

8. Architecture of UML: The 4+1 View Model & Metamodeling

Software architecture represents the set of significant design decisions regarding the organization of a software system. In UML, architecture is addressed through two foundations: Philippe Kruchten's 4+1 View Architectural Model and the OMG Four-Layer Metamodeling Architecture (M0 to M3).

8.1 Philippe Kruchten's 4+1 View Model

This model recognizes that software architecture cannot be captured through a single visual projection because different stakeholders (end users, programmers, systems engineers, project managers) possess orthogonal concerns. The architecture is therefore decomposed into five concurrent views:

Figure 1.9: Kruchten's 4+1 View Architectural Model of UML
View Stakeholder Concerns Addressed UML Diagrams
Use Case View (+1) End-users, Business Analysts Validates functional requirements, system boundaries, and business goals. Central organizing pivot driving all four views. Use Case, Activity Diagrams
Logical / Design View Software Architects, Programmers Decomposes functionality into domain vocabulary: classes, interfaces, collaborations, design patterns. Addresses what the system does. Class, Object, State Machine Diagrams
Process View System Integrators, Concurrency Engineers Addresses runtime non-functional qualities: multi-threading, asynchronous messaging, synchronization, throughput, and deadlock avoidance. Sequence, Communication, Timing Diagrams
Implementation View Developers, Build Engineers Physical code modularization: source files, package hierarchies, compilation dependencies, binaries, and third-party libraries. Component, Package Diagrams
Deployment View Infrastructure Architects, Network Admins Physical hardware execution topology: compute nodes, cloud clusters, network protocols, load balancers, and persistent storage. Deployment Diagrams

8.2 The OMG 4-Layer Metamodeling Architecture (M0 to M3)

UML is architected upon a rigorous four-layer metamodel hierarchy standardized by the OMG. Each layer serves as an instance of the layer immediately above it:

Figure 1.10: The OMG Four-Layer Metamodeling Architecture (M0 to M3 MOF)
Layer Name Description & Examples
M3 Meta-Object Facility (MOF) The foundational root meta-metamodel that defines the grammar for creating metamodels. Defines concepts like MOF_Class and MOF_Property. Serves as the universal root for UML, CWM, and SysML.
M2 UML Metamodel The language definition of UML itself. Defines concepts such as Class, Property, Operation, AssociationEnd, State. Standardized in the OMG UML Superstructure document.
M1 User Model (Application Domain) The classes, interfaces, associations, and statecharts designed by application developers (e.g., BankAccount, Customer). Every M1 element is an instance of an M2 classifier.
M0 User Instances (Runtime) Concrete runtime objects executing in physical memory (e.g., johnsAccount allocated at heap address 0x7FFE120). Every M0 element is an instance of an M1 classifier.

Relationship Between Architecture and OOAD

UML diagrams map to each phase of the software lifecycle through the 4+1 views:

  • Analysis Phase: Use Case Diagrams define functional requirements (Use Case View). Domain Class Diagrams identify key entities (Logical View).
  • System Design Phase: Component and Package Diagrams organize code modules (Implementation View). Deployment Diagrams map software to hardware (Deployment View).
  • Object Design Phase: Detailed Class Diagrams with typed signatures, Sequence Diagrams for interaction protocols, and State Machine Diagrams for object lifecycles refine the Logical and Process Views.

9. Object-Oriented vs. Structured Modeling

University examinations frequently require a comparative analysis between traditional Structured Analysis & Design (SA/SD) and Object-Oriented Analysis & Design (OOAD).

Evaluation Metric Structured Analysis & Design (SA/SD) Object-Oriented Analysis & Design (OOAD)
Philosophy Top-down functional decomposition; views software as a pipeline transforming inputs to outputs. Entity decomposition; views software as an ecosystem of collaborative, autonomous agents.
Data & Function Coupling Strictly decoupled. Functions are active; data is passive and exposed in global stores. Tightly integrated through Encapsulation inside the class boundary.
Lifecycle Continuity Discontinuous: Significant semantic gap between analysis (DFDs) and design (Structure Charts). Seamless: Classes discovered during analysis carry directly into design and code.
Extensibility Low: New requirements cause cascading modifications across procedural files. High: Open-Closed Principle; new features added via polymorphic inheritance.
Real-World Fidelity Low: Deconstructs natural entities into fragmented process trees. High: Classes map 1-to-1 with domain concepts (Patient, Account).
Primary Artifacts Context DFD, Level-1 DFD, Data Dictionary, Structure Charts. Use Case, Class, Sequence, State Machine, and Deployment Diagrams.
Maintenance Cost High: Ripple effects across procedures make ongoing maintenance costly. Low: Class encapsulation confines changes to localized boundaries.

Comparative Example: Banking System

  • Under SA/SD: The system is decomposed into processes (Validate Account, Process Deposit, Calculate Interest) that read/write to flat data stores (ACCOUNT_LEDGER_TABLE). When a new account type (e.g., MoneyMarketAccount) is added, the schema update triggers breaking modifications across all existing subroutines.
  • Under OOAD: The system is decomposed into classes (Account base class, specialized into SavingsAccount, CheckingAccount, MoneyMarketAccount). Each subclass encapsulates its own rules behind the polymorphic method applyMonthlyMaintenance(). Adding new account types requires zero changes to the processing engine.
