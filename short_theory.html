Short Theory Compendium: Units 1, 2, and 3

This dedicated reference consolidates every short topic, theoretical concept, formal definition, architectural rule, and mathematical distinction across the BCS054 syllabus. Formatted for high revision efficiency and exam accuracy.

Unit 1: Introduction to Object Orientation & UML (Short Concepts)

1.1 Object Identity (OID)

Formal Definition: Object identity is the inherent, immutable characteristic of an object distinguishing it from all other computational entities, completely independent of its state values, class type, or variable name binding.

  • State vs. Identity: Two distinct objects can possess identical attribute values (e.g., two bank accounts each having holder "Alice" and balance $1,000), yet remain non-identical.
  • Equality (Value Match): objA.equals(objB) evaluates to true if attributes match.
  • Identity (Equivalence): &objA == &objB evaluates to true strictly if both point to the identical physical memory address.
  • Persistence: In relational databases, identity is enforced using surrogate primary keys (UUID, auto-increment integer IDs).

1.3 Polymorphism Classifications

Polymorphism allows a uniform interface invocation to trigger distinct type-specific operations:

  • Compile-Time (Static) Polymorphism: Resolved at compilation via early binding. Includes function overloading, operator overloading, and template parameterization. Carries zero runtime latency.
  • Runtime (Dynamic) Polymorphism: Resolved at execution via late binding using base pointers/references to derived classes with virtual functions. Implemented via Virtual Method Tables (VTable) and vptr indirection.

1.4 Generosity (Genericity / Parametric Polymorphism)

Formal Definition: The software engineering discipline of declaring classes, interfaces, and algorithms parameterized by data types, allowing maximum algorithmic reuse with strict compile-time type safety.

  • C++ Implementation: Monomorphized templates (e.g., template<typename T> class Vector { ... };). The compiler instantiates distinct machine code for each unique type argument, resulting in zero runtime indirection overhead.
  • Primary Advantages: Eliminates duplicate boilerplate algorithms, prevents unsafe void-pointer casting, and catches type mismatches at compile time.

1.5 The Four Principles of Modeling (Booch, Rumbaugh, Jacobson)

  1. The choice of model dictates how problems are attacked: Choosing an object model highlights domain entities and message contracts; choosing a functional data flow model highlights procedural pipelines.
  2. Models exist at multiple precision levels: Early conceptual models omit types to explore architecture; detailed design models specify full visibility, return types, and exceptions for code generation.
  3. The best models are connected to reality: Abstractions must directly mirror the semantics and topology of real-world domain requirements.
  4. No single model is sufficient: Non-trivial systems demand a small set of orthogonal views (static class structure, temporal sequence, reactive statechart, deployment topology).

1.6 Conceptual Model of UML: Building Blocks & Extensibility

The conceptual model of UML consists of three pillars:

  • Things: Structural (Class, Interface, Component, Node), Behavioral (Interaction, State Machine), Grouping (Package), Annotational (Note).
  • Relationships: Association (solid line), Dependency (dashed line with arrow), Generalization (solid line with hollow triangle), Realization (dashed line with hollow triangle).
  • Extensibility Mechanisms:
    • Stereotypes (<<...>>): Extends UML vocabulary with new model element semantics (e.g., <<interface>>, <<entity>>).
    • Tagged Values ({tag = value}): Adds metadata attributes to elements (e.g., {author = "Rishi", version = 2.1}).
    • Constraints ({expression}): Declares semantic rules and domain invariants (e.g., {ordered}, {balance >= 0}).

2.3 Link vs. Association

Link: A physical or conceptual tuple connection between concrete object instances at runtime (e.g., alice:Customer ——— acc101:Account). Contains no multiplicity.

Association: A class-level structural descriptor encompassing a collection of links sharing identical semantics, role names, and multiplicity cardinalities (e.g., Customer (1) ————— (1..*) Account).

2.4 Multiplicity & Quantification

  • 1 or 1..1: Exactly one instance.
  • 0..1: Optional (zero or one instance).
  • * or 0..*: Zero or more instances (arbitrary collection).
  • 1..*: At least one instance (non-empty collection).
  • m..n: Specified discrete bounded range (e.g., 2..4 players).
  • Qualified Association (Quantification): Attaches an indexing key attribute (e.g., [accountNumber]) to reduce target cardinality from 0..* down to 0..1.

2.6 Generalization vs. Inheritance

Generalization: An architectural relationship where a child classifier (subclass) inherits attributes, operations, and relationships from a parent classifier (superclass) — an conceptual "is-a" taxonomy.

Inheritance: The language-level implementation mechanism that executes generalization by allocating base class memory offsets and linking VTables in derived types.

2.7 Nested Generalization & Discriminators

Multiple inheritance combines two or more base classes simultaneously, risking ambiguity (the Diamond Problem). Nested Generalization decomposes complex taxonomies into single-inheritance tiers using discriminators (e.g., classifying Vehicle by discriminator environment [Land, Water], then sub-classifying by usage [Commercial, Private]).

2.8 Use Case Relationships: Include vs. Extend

  • <<include>>: Mandatory dependency. The base use case unconditionally invokes the included use case to complete its functional goal (e.g., Checkout includes Validate Payment).
  • <<extend>>: Optional dependency. The extending use case executes conditionally at a designated extension point under specific guard conditions (e.g., Apply Coupon extends Checkout only if coupons exist).

2.9 Activity Diagrams: Swimlanes & Concurrency

  • Swimlanes: Column or row partitions organizing actions according to the specific domain actor, system module, or department responsible for executing them.
  • Fork Bar: Solid synchronization line splitting a single procedural thread into two or more concurrent parallel threads.
  • Join Bar: Solid synchronization line that waits for all incoming concurrent threads to complete before resuming sequential flow.

2.10 State Machine Transitions

Models the reactive lifecycle of an entity. Formal transition syntax:

Event (parameters) [Guard Condition] / Side-Effect Action

  • Event: External stimulus triggering the transition (e.g., coinInserted(val)).
  • Guard: Boolean expression evaluated when event occurs (e.g., [val >= price]).
  • Action: Executable computational statement executed during transition (e.g., / dispenseItem()).

2.11 Architectural Modeling: Component & Deployment

Component Diagram: Models modular software packages and interfaces. Visualizes Provided Interfaces (lollipop notation —○) specifying services published, and Required Interfaces (socket notation —() specifying dependencies needed.

Deployment Diagram: Models physical hardware execution topology. Depicts Nodes (3D cubic boxes representing servers, devices) and communication links (with protocols: HTTPS, TCP/IP).

Unit 3: OOD, Optimization & Programming Style (Short Concepts)

3.1 Stages of Object-Oriented Design (OOD)

StageArchitectural ScopePrimary Deliverables
System Design (Macro)High-level strategic architectureSubsystems, concurrency strategy, data persistence, network topology, resource allocation.
Object Design (Micro)Detailed implementation blueprintsAlgorithm selection, concrete data structures, access optimizations, API visibility enforcement.

3.2 Rumbaugh's OMT 3 Models

  • Object Model (Structure - "WHAT"): Captures static domain entities, attributes, and relationships using Class Diagrams.
  • Dynamic Model (Control - "WHEN"): Captures temporal state changes and reactive events using Statecharts and Sequence Diagrams.
  • Functional Model (Transformation - "HOW"): Captures mathematical computations and data mutations using Data Flow Diagrams (DFDs).

3.3 Design Optimization Strategies

  1. Redundant Associative Paths: Adding cached shortcut pointers to bypass deep traversal chains ($O(1)$ direct lookup vs $O(N)$ traversal).
  2. Caching Derived Attributes: Storing computed values (e.g., totalPrice, gpa) in memory when read queries heavily exceed write updates.
  3. Execution Path Rearrangement: Reordering boolean evaluation clauses so the most selective filters execute first.

3.4 Inheritance Adjustment

  • Factoring Common Behavior: Consolidating identical attributes and methods discovered across disparate subclasses into a shared abstract base class.
  • Flattening Hierarchies: Removing intermediate trivial abstract classes that add VTable dispatch indirection without behavioral variation.
  • Delegation over Subclassing: Replacing misused inheritance with object composition when only partial functionality is required.

3.5 Translating Classes to Data Structures

  • Class Entities: Translated into C/C++ structs with contiguous field memory offsets.
  • 1-to-1 Associations: Mapped to direct object pointers or reference handles.
  • 1-to-Many / Many-to-Many Associations: Mapped to dynamic collection structures (dynamic arrays, linked lists, balanced binary trees, or hash tables).
  • Virtual Methods: Mapped to function pointer dispatch tables (VTables).

3.7 Mapping OOP Constructs to Procedural C

  • Classes: Mapped to C typedef struct { ... } ClassName;.
  • Methods: Mapped to C functions receiving an explicit self pointer as their first argument: void Class_method(ClassName* self, int arg);.
  • Inheritance: Base class struct embedded as the first member (at offset 0) of the derived struct.
  • Polymorphism: Structs embed a pointer `vptr` referencing a static table of function pointers.
