Unit II • Modeling & Architecture

Unit II: Structural, Behavioral, and Architectural Modeling

An exhaustive guide to UML structural models (Class & Object diagrams), dynamic interaction models (Sequence & Collaboration diagrams), behavioral workflows (Use Case, Activity, State Machine, Timing, Package diagrams), and physical architecture (Component & Deployment diagrams).

1. Basic Structural Modeling

Structural modeling captures the static skeleton of an object-oriented system. It defines the vocabulary of the application domain, the internal attribute/operation structures of classes, and the relationships connecting them.

1.1 Classes and Visibility Specifiers

A UML Class is rendered as a 3-compartment rectangle displaying Class Name, Attributes, and Operations.

VISUAL UML CLASS COMPARTMENT STRUCTURE
<<domain-entity>> BankAccount
- accountNumber : int
- balance : double = 0.0
# accountHolder : string
+ deposit(amount : double) : bool
+ withdraw(amount : double) : bool
+ getBalance() const : double
~ calculateInterest() : void
Symbol Visibility Mode Access Scope & Semantics
+PublicGlobally accessible by any system element.
-PrivateAccessible only within member methods of the declaring class.
#ProtectedAccessible by the declaring class and its derived subclasses.
~PackageAccessible by any element residing within the same package or namespace.

1.2 Structural Relationships

Relationship Visual Notation Description & Multiplicity Cardinality
Association ──[1]──────[0..*]── Structural connection describing links between object instances. Multiplicity bounds indicate cardinality (1, 0..1, 1..*, *).
Aggregation ◇────────────────── Weak "has-a" whole-part relationship where contained parts survive independently if the whole is destroyed (e.g., Department and Professor).
Composition ◆────────────────── Strong "part-of" whole-part relationship where the lifetime of parts is bound strictly to the whole (e.g., House and Rooms).
Generalization ──────────────────▷ "Is-a" taxonomic inheritance hierarchy where derived classes inherit state and behavior from a base class.
Dependency - - - - - - - - - > "Uses" transient relationship where changes in the supplier element can affect the client element.
Realization - - - - - - - - - ▷ Contractual implementation of an interface specification by a concrete class.

3. Interaction Diagrams (Collaboration & Sequence)

3.1 Collaboration Diagrams (Communication Diagrams)

A Collaboration Diagram emphasizes the structural organization and relationships among participating objects. Sequence ordering is denoted explicitly using numbered message strings.

VISUAL COLLABORATION DIAGRAM: ORDER SUBMISSION FLOW
user : Client
1: submitOrder(items) ->
controller : OrderCtrl
1.1: processPayment() ->
gw : PaymentGateway

3.2 Sequence Diagrams

A Sequence Diagram emphasizes the explicit chronological time ordering of messages exchanged between objects along vertical lifelines.

VISUAL SEQUENCE DIAGRAM: ASYNCHRONOUS AUTHENTICATION WITH CALLBACK
User
AuthClient
AuthServer
Database
1. [User -> AuthClient]: login(user, password) (Synchronous Call)
2. [AuthClient -> AuthServer]: asyncVerify(creds) (Asynchronous Message)
3. [AuthServer -> Database]: queryUser(user) (Synchronous Query)
4. [Database - - -> AuthServer]: returnUserData (Return Message)
5. [AuthServer -> AuthClient]: onAuthCallback(token) (Asynchronous Callback)

Unit II Summary

  • Class Diagrams define static elements, visibility specifiers, and relationships (Association, Aggregation, Composition, Generalization, Dependency).
  • Interaction Diagrams model message passing: Sequence Diagrams prioritize chronological timing; Collaboration Diagrams prioritize structural object layouts.
  • Behavioral Diagrams specify workflows (Activity Diagrams with forks/joins/swimlanes), requirements (Use Cases with include/extend), and state changes (State Machines).
  • Architectural Modeling employs Component Diagrams (provided/required interfaces) and Deployment Diagrams (nodes and physical artifacts).

Short Answer Questions (2–3 Marks)

2 Marks Differentiate between Aggregation and Composition with UML notations.

Model Answer:

  • Aggregation (◇───────): Weak "has-a" whole-part relationship where parts survive the destruction of the whole (e.g., Department and Professor).
  • Composition (◆───────): Strong "part-of" whole-part relationship where parts are destroyed along with the whole (e.g., House and Rooms).
2 Marks Explain the difference between <<include>> and <<extend>> in Use Case diagrams.

Model Answer:

  • <<include>>: Unconditionally executes the included use case as a mandatory sub-routine (e.g., Withdraw Cash includes Authenticate PIN).
  • <<extend>>: Conditionally executes optional behavior only when a specific extension point condition is met (e.g., Print Low Balance Warning extends Check Balance).
3 Marks What are Fork and Join nodes in an Activity Diagram?

Model Answer: Both are rendered as solid synchronization bars:

  • Fork: Splits one incoming control flow into multiple concurrent parallel flows.
  • Join: Synchronizes multiple incoming concurrent flows, waiting for all to finish before emitting a single outgoing flow.

Long Answer Questions (7–10 Marks)

10 Marks Draw and explain the Class Diagram and Object Diagram for an E-Commerce Order Management System.

Model Answer Structure:

  1. Draw Class Diagram with Customer, Order, OrderItem, Product, Address.
  2. Specify attributes, visibility (+, -, #), operations, and multiplicities (1, 1..*, 0..*).
  3. Draw corresponding Object Diagram snapshot with underlined instance names (cust101 : Customer) and concrete values.
  4. Contrast the abstract static nature of Class Diagrams with the runtime state snapshot of Object Diagrams.
10 Marks Explain Architectural Modeling in UML. Compare Component and Deployment Diagrams with clear architectural illustrations.

Model Answer Structure:

  • Component Diagram: Explain components, provided interfaces (ball ───O), required interfaces (socket ───(), and software packaging.
  • Deployment Diagram: Explain computational nodes, devices, execution environments, network protocols, and deployed physical artifacts.
  • Draw an integrated 3-Tier Web Architecture showing both diagrams.
