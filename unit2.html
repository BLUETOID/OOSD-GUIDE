Unit 2: Basic Structural, Behavioural & Architectural Modeling

This module covers the complete Unit 2 syllabus: Basic Structural Modeling (Classes, Relationships, Links, Associations, Multiplicity, Aggregation, Composition, Generalization), Behavioral Modeling (Use Cases, Sequence Diagrams, Collaboration Diagrams, Activity Diagrams with Swimlanes, State Machine Diagrams), and Architectural Modeling (Component & Deployment Diagrams).

1. Classes & Visibility Specifiers

A Class is the fundamental building block of structural modeling. It represents a blueprint describing domain entities that share identical attributes, operations, relationships, and behavioral semantics. In UML, a class is rendered as a 3-compartment rectangle:

Figure 2.1: Standard UML 3-Compartment Class Notation

The three compartments are: 1) Class Name (centered, bold), 2) Attributes (visibility prefix, name, type, optional default), 3) Operations (visibility prefix, name, parameters, return type). Static members are underlined.

Symbol Visibility Scope & Accessibility Architectural Intent
+PublicAccessible to all classifiers across the entire system.Defines the public service contract / interface.
-PrivateAccessible exclusively within the declaring class methods.Enforces information hiding; prevents illegal state mutation.
#ProtectedAccessible within the declaring class and all derived subclasses.Enables controlled inheritance specialization.
~PackageAccessible only by classifiers in the same package.Enforces component-level modularity boundaries.

2. Link vs Association

Understanding the distinction between Links and Associations is fundamental to structural modeling:

Facet Link (Instance Level) Association (Class Level)
DefinitionA concrete connection between specific runtime object instances.A structural descriptor describing a group of links with common semantics.
Semantic LevelM0 Level — exists at runtime in physical memory.M1 Level — exists as a model element in the design.
Visual NotationSolid line between underlined instance names, no multiplicity.Solid line between class boxes with name, role names, and multiplicity.
LifetimeDynamic; created and destroyed at runtime.Static; permanently declared in source code / schema.
RelationshipA link is an instance of an association.An association is a classifier of its links.
Examplejohn:Employee ——— it:DepartmentEmployee 1..* ——— 1 Department

3. Multiplicity & Quantification (Qualified Associations)

Multiplicity specifies the allowable cardinality range of instances that can participate in a relationship:

Notation Meaning Example
1 or 1..1Exactly one instanceA Country has exactly 1 capital City.
0..1Optional (zero or one)A Person may have 0..1 Passport.
* or 0..*Zero or moreA Library holds 0..* Book instances.
1..*At least one (non-empty)A Department must have 1..* Employee.
m..nBounded rangeA Team has 2..11 Player members.

Qualified Associations (Quantification)

In large collections, traversing an association yields an O(N) lookup. A Qualified Association partitions the target collection using an indexing key attribute called a qualifier, reducing target multiplicity from 0..* to 0..1 — equivalent to a dictionary/map lookup.

Figure 2.3: Qualified Association — accountNumber reduces multiplicity from 0..* to 0..1

Example: Without qualification, Bank has 0..* Account objects. With the qualifier accountNumber, a specific account can be looked up in O(1) time, reducing the effective multiplicity to 0..1 per key.

4. Aggregation vs Composition (Whole-Part Modeling)

Both aggregation and composition represent "whole-part" relationships, but they differ fundamentally in lifetime coupling and ownership semantics:

Criteria Aggregation (Shared) Composition (Composite)
Lifecycle CouplingWeak: Parts have independent existence. If the whole is deleted, parts continue to exist.Strong: Parts belong exclusively to one whole. Destroying the whole cascades to destroy all parts.
UML NotationHollow open diamond at whole end: ◇————Solid filled diamond at whole end: ◆————
SharingParts may be shared among multiple aggregates simultaneously.A part can belong to strictly one whole at any instant.
C++ MappingRaw pointers, references, or std::shared_ptr.Direct member objects or std::unique_ptr.
Domain ExampleUniversity ◇—— Professor (professors survive university closure)Building ◆—— Room (demolishing building destroys rooms)
Figure 2.4: Aggregation vs Composition with Combined Car Example
// Aggregation: Weak relationship (Department references Teacher; Teacher exists independently)
class Department { Teacher* teacher; };

// Composition: Strong relationship (House owns Room; lifecycle tightly coupled)
class House { Room rooms[4]; };

5. Generalization, Inheritance & The Diamond Problem

Generalization is the taxonomic "is-a" relationship where a child classifier inherits all attributes, operations, and relationships of the parent classifier. The UML notation is a solid line with a hollow triangular arrowhead pointing to the parent.

Inheritance is the concrete programming language mechanism that implements generalization by copying member definitions to derived classes.

FacetGeneralization (Conceptual)Inheritance (Implementation)
LevelAnalysis/Design model (UML)Programming language (C++, Java)
NotationSolid line + hollow triangle → parentclass Dog : public Animal {}
TypesSingle, Multiple, Multilevel, HierarchicalSame, plus virtual inheritance for diamond resolution

The Diamond Problem in Multiple Inheritance

When class D inherits from classes B and C, which both inherit from base class A, class D receives duplicate copies of A's attributes, creating compilation ambiguity and memory waste.

Figure 2.5: Classic Diamond Problem in Multiple Inheritance

C++ Virtual Base Class Solution

// Virtual Base Class: Resolves diamond multiple inheritance
class Device { public: int voltage; };
class Scanner : virtual public Device {};
class Printer : virtual public Device {};
class Copier  : public Scanner, public Printer {}; // Single shared Device subobject

7. Sequence Diagrams (Time-Ordered Interactions)

Sequence diagrams model the chronological ordering of messages exchanged between object lifelines. They are the most widely used interaction diagram.

Key Elements

  • Lifeline: Vertical dashed line extending below each participating object, representing its existence over time.
  • Activation Bar (Focus of Control): Thin rectangle on the lifeline indicating the period during which an object is executing an operation.
  • Synchronous Call (Solid line, filled arrowhead ▶): Sender blocks and waits for the receiver to complete processing and return.
  • Asynchronous Call (Solid line, open arrowhead →): Sender continues execution immediately without blocking for a response.
  • Return Message (Dashed line, open arrowhead -→): Control passes back to the caller with optional return value.
  • Self-Call: An object invokes its own method, shown as a message arrow looping back to the same lifeline.
  • Callback: The receiver invokes a method back on the original sender during processing.
  • Broadcast Message: A message sent to all objects in the system simultaneously (shown as arrows to multiple lifelines from a single source).
Figure 2.7: Sequence Diagram — Synchronous, Asynchronous, Return Messages & Callback

8. Collaboration (Communication) Diagrams

Collaboration diagrams emphasize the structural link topology between objects rather than time ordering. Messages are labeled with hierarchical sequence numbers.

Key Differences from Sequence Diagrams

FacetSequence DiagramCollaboration Diagram
Primary FocusTime ordering of messages (vertical axis = time)Structural link topology between objects
Message OrderingImplicit from vertical position (top-to-bottom)Explicit via hierarchical numbering: 1:, 1.1:, 1.2:
LayoutObjects on horizontal axis, time flows downFree-form spatial arrangement of objects and links
PolymorphismShown via multiple lifelines for different subclassesShown by dispatching a message to an abstract role bound to concrete subtypes
EquivalenceBoth are semantically equivalent (isomorphic). Any sequence diagram can be mechanically converted to a collaboration diagram and vice-versa.

9. Use Case Diagrams

Use Case diagrams capture system boundaries and functional requirements from the perspective of external actors. They answer: "What does the system do for its users?"

Key Elements

  • Actor (Stick Figure): Any external person, device, or system interacting with the software.
  • Use Case (Ellipse): A coherent unit of functionality delivering observable value to an actor. Named with a verb phrase (e.g., "Place Order").
  • System Boundary (Rectangle): Encloses all use cases that belong to the system under design.
  • «include»: Mandatory inclusion — the base use case always invokes the included use case. Shown as a dashed arrow from base to included use case.
  • «extend»: Optional conditional behavior triggered at an extension point. Shown as a dashed arrow from extending to base use case.
  • Generalization: An actor or use case inheriting behavior from a more general actor/use case.

10. Activity Diagrams & Swimlanes

Activity diagrams model procedural logic, concurrent algorithms, and business workflows. They are similar to flowcharts but support concurrency via fork/join constructs.

Key Elements

  • Initial Node (Filled circle): Entry point of the activity.
  • Final Node (Circled filled circle): Termination point.
  • Action States (Rounded rectangles): Atomic execution steps.
  • Decision Diamond: Conditional routing governed by boolean guards [condition].
  • Merge Diamond: Joins multiple alternative paths back into one flow.
  • Fork Bar (Solid horizontal bar): Splits execution into concurrent parallel threads.
  • Join Bar (Solid horizontal bar): Synchronizes — waits for all concurrent threads to complete before continuing.
  • Swimlanes: Vertical or horizontal column partitions that assign explicit organizational responsibility for each action to a specific actor, department, or subsystem.

11. State Machine Diagrams (Statecharts)

State Machine diagrams model the reactive lifecycle of an object as a finite state automaton. They show how an object traverses discrete states in response to events.

Transition Signature

Each transition follows the format: Event (parameters) [Guard condition] / Action

  • State (Rounded rectangle): A discrete condition during which the object satisfies certain constraints, performs an activity, or waits for an event.
  • Transition (Arrow): Directed edge from source state to target state, triggered by an event.
  • Initial Pseudo-state (Filled circle): Entry point — the starting state.
  • Final State (Circled filled circle): Termination.
  • Entry/Exit Actions: Actions automatically executed when entering or leaving a state: entry / action, exit / action.

12. Component Diagrams

Component diagrams model the physical software modularity — how code is organized into deployable components such as JARs, DLLs, Docker containers, or web assemblies.

Key Elements

  • Component: Rectangle with component icon (tabs) or «component» stereotype.
  • Provided Interface (Lollipop ○—): An interface that the component exports — services it offers to other components.
  • Required Interface (Socket —⊃): An interface that the component needs from another component to function.
  • Dependency: Dashed arrow showing that one component relies on another.
Figure 2.13: Component Diagram with Provided/Required Interfaces

13. Deployment Diagrams

Deployment diagrams model the physical hardware execution topology — how software artifacts are allocated to computational nodes.

Key Elements

  • Node (3D Cuboid): A physical computational resource possessing memory and processing capacity (server, VM, mobile device, IoT sensor).
  • Execution Environment: A node within a node — e.g., an application server running inside a physical host.
  • Artifact: A physical file deployed on a node (WAR, JAR, binary, config file).
  • Communication Path: A line between nodes annotated with the protocol used (HTTPS, TCP/IP, JDBC, gRPC).
