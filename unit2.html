Unit 2: Basic Structural, Behavioural & Architectural Modeling

This module provides an exhaustive architectural breakdown of UML modeling across static structure, dynamic temporal interactions, reactive state mechanics, and physical deployment topologies.

1. Classes & Visibility Specifiers

A Class represents a structural blueprint describing domain entities that possess identical attributes, operations, relationships, and behavioral semantics. In UML, a class is rendered as a 3-compartment rectangle.

+ Public Accessible unconditionally to all classifiers across the system. Defines the public service contract / interface.
- Private Accessible exclusively within the declaring class methods. Enforces information hiding; prevents illegal state mutation.

2. Structural Relationships & Semantics

UML defines four fundamental structural relationships connecting classes:

A. Link vs. Association

Facet Link (Instance Level) Association (Class Level)
Semantic Level A concrete connection between specific runtime object instances. A structural descriptor describing a group of links with common semantics.
Visual Notation Solid line between underlined instance names without multiplicity: e1:Employee ——— d1:Dept Solid line between class boxes with name, role names, and multiplicity: 1..* ————— 1
Temporal Lifetime Dynamic; created and destroyed at runtime. Static; permanently declared in source code / schema.

3. Multiplicity & Quantification (Qualified Associations)

Multiplicity specifies the allowable cardinality range of instances that can be linked to a single instance of another class:

  • 1 or 1..1: Exactly one instance.
  • 0..1: Optional (zero or one instance).
  • * or 0..*: Zero or more instances (arbitrary collection).
  • 1..*: At least one instance (non-empty collection).
  • m..n: Discrete bounded range (e.g., 2..4 players).

Qualified Associations (Quantification)

In large collections, traversing an association yields a many-to-one or many-to-many lookup ($O(N)$ search). A Qualified Association partitions the target collection using an indexing key attribute called a qualifier, reducing target multiplicity from 0..* to 0..1 (equivalent to an associative map or dictionary in code).

4. Aggregation vs. Composition (Whole-Part Modeling)

Both aggregation and composition represent "whole-part" relationships, but they differ fundamentally in lifetime coupling and ownership semantics:

Evaluation Criteria Aggregation (Shared Whole-Part) Composition (Composite Whole-Part)
Lifecycle Coupling Weak: The "part" has an independent existence outside the "whole". If the whole is deleted, parts continue to exist. Strong: The "part" belongs exclusively to one whole. Destruction of the whole cascades to destroy all parts.
UML Glyph Hollow open diamond at whole end: <>———— Solid filled diamond at whole end: <*>-———
Sharing Semantics Parts may be shared simultaneously among multiple aggregates. Part can belong to strictly one whole at any given instant.
C++ Implementation Raw pointers, references, or std::shared_ptr. Direct member object embedding or std::unique_ptr.
Domain Example University <>— Professor (professors survive university closure). Building <*>- Room (demolishing building destroys rooms). 
// C++ Concrete Implementation of Aggregation vs Composition
#include <iostream>
#include <vector>
#include <memory>

// --- AGGREGATION: Professor exists independently ---
class Professor {
public:
    std::string name;
    Professor(std::string n) : name(n) {}
};

class Department {
public:
    std::vector<Professor*> faculty; // Holds non-owning pointers (Aggregation)
    void addProfessor(Professor* p) { faculty.push_back(p); }
    // Destructor does NOT delete faculty members!
};

// --- COMPOSITION: Room lifetime is bound to Building ---
class Room {
public:
    int roomNumber;
    Room(int num) : roomNumber(num) {}
    ~Room() { std::cout << "Room " << roomNumber << " destroyed.\n"; }
};

class Building {
public:
    std::vector<std::unique_ptr<Room>> rooms; // Owning smart pointers (Composition)
    void addRoom(int num) {
        rooms.push_back(std::make_unique<Room>(num));
    }
    // When Building is deleted, all Rooms are automatically destroyed!
};

5. Generalization, Multiple Inheritance & The Diamond Problem

Generalization: An architectural relationship where a child classifier (subclass) inherits the structural features and behavioral contracts of its parent classifier (superclass) — an conceptual "is-a" relationship.

The Diamond Problem in Multiple Inheritance

When class $D$ inherits from classes $B$ and $C$, which both inherit from base class $A$, class $D$ receives duplicate copies of $A$'s attributes. This creates compilation ambiguity when referencing $A$'s members and wastes memory.

Figure 2.3: Classic Diamond Problem Taxonomy in Multiple Inheritance

The C++ Virtual Base Class Solution

#include <iostream>

class PoweredDevice {
public:
    int voltage;
    PoweredDevice(int v) : voltage(v) {
        std::cout << "PoweredDevice initialized with " << v << "V.\n";
    }
};

// Virtual base class inheritance eliminates duplicate base instances
class Scanner : virtual public PoweredDevice {
public:
    Scanner(int v) : PoweredDevice(v) {}
};

class Printer : virtual public PoweredDevice {
public:
    Printer(int v) : PoweredDevice(v) {}
};

// Copier directly initializes the single shared PoweredDevice instance
class Copier : public Scanner, public Printer {
public:
    Copier(int v) : PoweredDevice(v), Scanner(v), Printer(v) {}
};

int main() {
    Copier c(220);
    std::cout << "Operating Voltage: " << c.voltage << "V\n"; // Unambiguous!
    return 0;
}

6. Class Diagrams vs. Object Diagrams

Facet Class Diagram Object Diagram
Underlying Concept Abstract blueprint; specifies types, operations, and allowable system states. Concrete instance graph; captures a snapshot of physical memory at time $t$.
Naming Convention Class Name (e.g., Order). Underlined name: order101 : Order.
Attribute Representation Names, data types, visibility: - totalAmount : double. Concrete literal values: totalAmount = 249.99.
Link Notation Associations with multiplicity ranges (1..*, 0..1). Links without multiplicity (cardinality is inherently 1-to-1 at runtime).

7. Dynamic Interaction Modeling

UML provides two complementary interaction diagrams to capture dynamic behavior:

A. Sequence Diagrams (Time-Ordered)

Sequence diagrams model chronological message flow along vertical dashed lifelines. Notations include:

  • Synchronous Call (Solid line, filled arrow ▲): Sender blocks waiting for return.
  • Asynchronous Call (Solid line, open arrow →): Sender resumes immediately without blocking.
  • Return Message (Dashed line, open arrow -->): Control passes back to caller.
  • Activation Bar (Focus of Control): Vertical rectangle indicating active thread execution.

B. Collaboration Diagrams (Spatial Topology)

Collaboration (Communication) diagrams highlight object connections. Messages use procedural sequence numbering: 1: request(), 1.1: validate(), 1.2: calculate(), 2: returnReceipt().

8. Use Case Modeling

Captures system boundaries and functional requirements from the perspective of external actors.

  • Actor (Stick Figure): Any external person, physical device, or external system interacting with the software.
  • Use Case (Ellipse): A coherent unit of functional functionality delivering observable value to an actor.
  • <<include>>: Mandatory inclusion. Base use case cannot complete without executing the included use case.
  • <<extend>>: Optional conditional behavior triggered at designated extension points.

9. Activity Diagrams & Swimlanes

Activity diagrams model procedural logic, concurrent algorithms, and business workflows.

  • Action States (Rounded rectangles): Atomic execution steps.
  • Decision & Merge Diamonds: Conditional routing governed by boolean guards [condition].
  • Fork and Join Bars: Solid bars splitting execution into concurrent threads (Fork) and waiting for all branches to finish before continuing (Join).
  • Swimlanes: Column partitions establishing explicit organizational responsibility for each action across departments or services.

10. State Machine Diagrams (Statecharts)

Statecharts model the reactive lifecycle of an object as a finite state automaton. Transition signature: Event (params) [Guard] / Action.
