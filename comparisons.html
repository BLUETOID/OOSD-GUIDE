Category I: Paradigms & Core Object Concepts (Unit 1 & 3)

1. Procedural Programming (POP) vs. Object-Oriented Programming (OOP)

PYQ: [2020-21], [2022-23]
Criterion Procedural Programming (POP) Object-Oriented Programming (OOP)
Core Focus Action/Verb-centric: Emphasizes step-by-step procedures, algorithms, and function calls. Noun/Entity-centric: Emphasizes autonomous domain objects integrating state and behavior.
Problem Decomposition Top-Down: Large problems are decomposed hierarchically into smaller subroutines and functions. Bottom-Up: Autonomous classes are formulated, encapsulated, and assembled into subsystems.
Data & Logic Binding Data is passive and separated from functions. Passed via parameters or held globally. Data and methods are tightly coupled within a cohesive boundary (Class).
Data Access Security Low; global data is accessible and mutable by any procedure across the codebase. High; information hiding via access specifiers (private, protected, public).
Control Flow Sequential execution with branching and explicit subroutine jump-and-return calls. Message passing between objects; dynamic polymorphic runtime dispatch.
Code Reuse Limited to static procedural library functions; high risk of side effects. Inheritance hierarchies, parametric polymorphism (templates), and delegation.
Maintenance Impact Altering a shared data structure causes cascading modifications across all dependent functions. Internal changes to a class do not impact clients if public method contracts remain invariant.

Exam Takeaway: POP divides programs by functions operating on passive shared data; OOP divides programs by autonomous entities bundling private data with authorized operations.

2. Object Identity vs. Object Equality

PYQ: [2020-21], [2025-26]
Criterion Object Identity (OID) Object Equality (Equivalence)
Fundamental Concept The unique, immutable property of an object distinguishing it from all other objects in the universe. The property where two distinct objects possess identical internal state attribute values.
Dependence on State Completely independent of state. Two objects remain non-identical even if all attributes match. Strictly dependent on current state values at a given moment in time.
Physical Implementation Physical memory address (pointer address) or surrogate database primary key (UUID). Value-by-value comparison via overloaded operators (operator==) or equals().
Mutability Permanent and immutable throughout the entire lifecycle of the object. Dynamic; two equal objects become unequal as soon as an attribute mutates.
Real-World Analogy Identical twin humans with unique Aadhaar/SSN numbers and distinct physical bodies. Two identical $100 currency bills having the exact same face value, but distinct serial numbers.

Exam Takeaway: Identity answers "Is this the exact same instance in memory?" (&a == &b); Equality answers "Do these two instances have the same data values?" (a.equals(b)).

3. Data Abstraction vs. Data Encapsulation

PYQ: [2020-21], [2024-25], [2025-26]
Criterion Data Abstraction ("WHAT") Data Encapsulation ("HOW")
Primary Question "WHAT" does the entity do? (Observable external behavior). "HOW" is the entity implemented internally? (Containment & packaging).
Architectural Purpose Reduces cognitive complexity by exposing only essential features while ignoring irrelevant background details. Protects internal state integrity, prevents unauthorized mutation, and enforces class invariants.
Implementation Mechanism Abstract base classes, pure virtual interfaces, function prototypes, and API contracts. Classes combining data + methods, access specifiers (private), accessor/mutator methods.
Focus of Attention Focuses on the external interface boundary seen by client developers. Focuses on the internal structural implementation hidden from client developers.
Automobile Analogy Steering wheel, accelerator, and brake pedals providing a clean driving interface. Pistons, transmission gears, and spark plugs sealed safely beneath the vehicle hood.

Exam Takeaway: Abstraction hides complexity by exposing a minimal interface; Encapsulation hides internal data and implementation to safeguard integrity.

4. Encapsulation vs. Information Hiding

PYQ: [2021-22], [2024-25]
Criterion Encapsulation Information Hiding
Definition The programmatic packaging mechanism of bundling data and its associated operations into a unified construct (Class). The software design principle of deliberately concealing design decisions and internal structures likely to change.
Nature A structural packaging mechanism provided by programming language syntax. A high-level architectural design principle (Parnas's Principle) guiding modular decomposition.
Visibility Implication Encapsulation can be public or private (e.g., public methods are encapsulated inside the class). Information hiding strictly restricts visibility, making internal structures inaccessible outside the module.
Role in Architecture Acts as the vehicle/container through which information hiding is enforced. Acts as the strategic rationale determining what to place into private scope.

Exam Takeaway: Encapsulation is the mechanism of putting data and functions into a capsule; Information Hiding is the design rule that makes the inside of the capsule invisible.

5. Static (Compile-Time) vs. Dynamic (Runtime) Polymorphism

PYQ: [2023-24]
Criterion Static (Compile-Time) Polymorphism Dynamic (Runtime) Polymorphism
Binding Time Early Binding: Function call is resolved and bound to concrete code during compilation. Late / Dynamic Binding: Method address is resolved dynamically during program execution.
Enforcement Mechanisms Function Overloading, Operator Overloading, and Parametric Templates (Generics). Inheritance hierarchies with virtual member functions and overriding.
Execution Overhead Zero runtime penalty; calls are direct assembly jumps or inlined machine code. Small runtime cost: extra memory for vptr per object and VTable pointer indirection.
Flexibility Lower runtime adaptability; types must be completely known at compile time. Maximum runtime extensibility; new derived classes can be plugged in without recompilation.

Exam Takeaway: Static polymorphism binds method addresses at compile-time (fast, rigid); dynamic polymorphism binds method addresses at runtime via VTable dispatch (flexible, extensible).

6. Structured Modeling vs. Object-Oriented Modeling

PYQ: [2024-25], [2025-26]
Criterion Structured Modeling (SA/SD) Object-Oriented Modeling (OOM)
Core Unit of Analysis Functions and processes that transform inputs into outputs (Pipelines). Autonomous objects encapsulating private attributes and behavior (Domain Models).
Primary Artifacts Data Flow Diagrams (DFDs), Structure Charts, Data Dictionaries. UML Class, State Machine, Sequence, and Component Diagrams.
Semantic Gap Large: Analysis models (DFDs) must be completely restructured to create design models (Structure Charts). Minimal: Seamless semantic continuity; analysis classes map directly to design and code classes.
Resilience to Change Fragile; modifying a shared data schema requires updating all dependent functional modules. Robust; encapsulated classes isolate internal data modifications behind public contracts.

Exam Takeaway: Structured modeling organizes software around functions; OO modeling organizes software around domain entities.

Category II: Structural Modeling & Class Relationships (Unit 2)

7. Link vs. Association

PYQ: [2020-21], [2021-22], [2025-26]
Figure C.1: Structural Mapping from Abstract Class Association to Concrete Runtime Object Link
Criterion Link Association
Abstraction Level Instance Level: A concrete physical or conceptual connection connecting specific object instances. Class/Classifier Level: A conceptual description of a group of links sharing identical semantics and attributes.
Diagrammatic Context Rendered on Object Diagrams and Collaboration Diagrams. Rendered on Class Diagrams.
Multiplicity Notation Zero Multiplicity: A link is an individual instance connection; multiplicity is meaningless on a link. Explicit Multiplicity: Defines legal cardinality ranges (1, 0..1, *, 1..*) at association ends.
Naming Convention Underlined name (e.g., worksFor) connecting underlined object instances. Plain text name with direction triangle (e.g., worksFor >) connecting class boxes.
Mathematical Theory A single tuple in a relation: $(obj_A, obj_B) \in R$. The mathematical relation $R$ defined over Cartesian product $Class_A \times Class_B$.

Exam Takeaway: A Link is to an Association as an Object is to a Class. A link connects individual objects at runtime; an association describes legal connections between classes.

8. Generalization vs. Inheritance

PYQ: [2020-21], [2023-24]
Criterion Generalization (UML Analysis Concept) Inheritance (Programming Language Mechanism)
Conceptual Domain Analysis & Modeling Space: The semantic relationship between a general classifier (superclass) and specialized classifiers (subclasses). Implementation Space: The technical language mechanism enabling a class to absorb attributes and methods from an ancestor.
Relationship Direction Bottom-Up or Top-Down: Generalization moves bottom-up (extracting common traits); Specialization moves top-down. Unidirectional: Subclasses mechanically derive properties from parent classes.
Semantic Meaning Strict "is-a-kind-of" taxonomic classification adhering to the Liskov Substitution Principle (LSP). Code reuse mechanism; can be misused purely for convenience even when subtyping is violated.
Visual Notation Solid directed vector with a large hollow triangle pointing toward the general superclass. Language keywords: extends (Java), : public (C++), class Child(Parent): (Python).

Exam Takeaway: Generalization is the conceptual taxonomic relationship (Design); Inheritance is the programming mechanism that implements it (Code).

9. Aggregation (Shared) vs. Composition (Composite / Non-Shared)

PYQ: [2021-22], [2025-26]
Figure C.2: UML Notational Difference between Hollow Diamond (Aggregation) and Filled Diamond (Composition)
Criterion Aggregation (Shared Association) Composition (Composite Aggregation)
Coupling Strength Weak "has-a" relationship: The part can exist independently of the whole. Strong "part-of" relationship: The part has no independent existence outside the whole.
Lifecycle Co-incidence Independent lifecycles: Destroying the whole (Department) does NOT destroy the parts (Teachers). Strictly co-incident lifecycles: Destroying the whole (Building) cascades and automatically destroys all parts (Rooms).
Ownership Exclusivity Shared: A part instance may belong to multiple whole aggregations concurrently. Exclusive (Unshared): A part instance can belong to exactly ONE composite whole at any given time.
UML Graphical Notation A hollow (unfilled) diamond at the whole aggregate end of the association line. A solid (filled) black diamond at the composite whole end of the association line.
Multiplicity on Whole End Can be any valid multiplicity (0..1, 1, *). Must strictly be exactly 1 or 0..1 (never *).

Exam Takeaway: In Aggregation (hollow diamond), parts survive when the whole is deleted. In Composition (filled diamond), parts die when the whole is deleted.

10. Class Diagram vs. Object Diagram

PYQ: [2023-24]
Criterion Class Diagram Object Diagram
Temporal Dimension Static Schema: Represents structural rules, types, and invariants valid for all time. Runtime Snapshot: Captures an instantaneous snapshot of system memory at a discrete point in time.
Core Entities Rendered Classes with attribute types, method signatures, and access modifiers. Specific object instances with concrete bound values (e.g., balance = 5000.0).
Entity Label Notation Standard text: ClassName (not underlined). Underlined syntax: instanceName : ClassName or anonymous : ClassName.
Relationships Shown Associations, Aggregations, Compositions, Generalizations with multiplicity bounds. Concrete Links connecting specific objects (zero multiplicity).
Engineering Role Architectural specification and design blueprint for implementation. Testing, test case design, and debugging complex structural configurations.

Exam Takeaway: A Class Diagram is the static architectural blueprint; an Object Diagram is an instantaneous snapshot of instantiated memory at runtime.

11. Comprehensive 4-Way Relationship Comparison Matrix

PYQ: [2021-22], [2022-23]
Relationship Type UML Visual Notation Semantic Meaning Coupling Level Lifecycle Binding Code Implementation
Association Solid line, optional open arrow for navigability Peer "uses-a" or structural link between independent classes. Loose Completely independent Pointer or reference attribute: Teacher* teacher;
Aggregation Hollow diamond on whole side Weak "has-a" whole-part containment; parts can exist without the whole. Medium-Loose Independent lifetimes Collection of pointers: vector<Student*> students;
Composition Solid filled diamond on whole side Strong "part-of" whole-part ownership; parts cannot survive without the whole. Strong Strictly co-incident Value members / nested objects: Engine engine;

Exam Takeaway: Association = peer link; Aggregation = shared part; Composition = owned part; Generalization = type classification.

Category III: Behavioral & Architectural Diagrams (Unit 2)

12. Sequence Diagram vs. Collaboration (Communication) Diagram

PYQ: [2020-21], [2022-23], [2025-26]
Criterion Sequence Diagram Collaboration (Communication) Diagram
Primary Emphasis Chronological Time Sequence: Emphasizes explicit time ordering of messages flowing top-to-bottom. Structural Spatial Context: Emphasizes architectural object organization, links, and topology.
Time Representation Geometric Y-axis: Time flows continuously downward along vertical dashed lifelines. Sequence Numbers: Time is expressed via decimal numbering prefixes (1.0, 1.1, 2.0) on message vectors.
Object Lifeline & Activation Features explicit vertical lifelines and rectangular activation focus bars. Zero lifelines: Objects are drawn as free-floating rectangles connected by solid structural links.
Concurrent & Complex Flows Superior for visualizing nested loops, alt blocks, and concurrent asynchronous message flows. Difficult to read when message cascades become deep or complex; becomes cluttered quickly.
Semantic Equivalence Isomorphic: Both are interaction diagrams that convey mathematically identical interaction information. A Sequence Diagram can be converted automatically into a Collaboration Diagram without data loss.

Exam Takeaway: Sequence diagrams emphasize time ordering down vertical lifelines; Collaboration diagrams emphasize structural links and object topology using numbered message labels.

13. Activity Diagram vs. State Machine (Statechart) Diagram

PYQ: [2025-26]
Criterion Activity Diagram State Machine Diagram (Statechart)
Fundamental Viewpoint Data/Control Workflow: Models procedural workflows, algorithms, and multi-actor business processes. Discrete State Transitions: Models the discrete internal states and lifecycle transitions of a single object.
Transition Triggers Automatic (Internal Completion): Transition fires automatically as soon as the activity finishes executing. Event-Driven (External): Transition fires strictly in response to an external asynchronous event trigger.
Concurrency Modeling Uses explicit Fork and Join synchronization bars and Swimlanes for role partitioning. Uses Orthogonal Composite States separated by dashed concurrency boundaries.
Swimlane Support Native Swimlanes: Partitions activities vertically/horizontally across business roles and departments. No swimlanes; focused entirely on the boundary of one reactive object.

Exam Takeaway: Activity diagrams model workflow execution driven by internal completion; State machine diagrams model reactive lifecycles driven by external events.

14. Use Case Include («include») vs. Extend («extend»)

PYQ: [2022-23], [2024-25]
Figure C.3: Vector Arrow Direction Contrast: «include» points to Included UC; «extend» points back to Base UC
Criterion «include» Dependency «extend» Dependency
Execution Obligation Mandatory / Unconditional: The base use case cannot complete without executing the included use case. Optional / Conditional: The extending use case executes only if a specific extension point predicate evaluates to true.
Arrow Direction Points FROM Base Use Case TO Included Use Case (Base → Included). Points FROM Extending Use Case BACK TO Base Use Case (Extending → Base).
Base Case Awareness The base use case is explicitly aware of the included use case and invokes it directly. The base use case is completely oblivious to the extending use case; declares only an extension point.
Primary Purpose Factoring out common, reusable behavior shared across multiple use cases (e.g., AuthenticateUser). Modeling optional branches, edge cases, add-on features, or exceptional flows (e.g., CalculateDiscount).

Exam Takeaway: «include» is mandatory and points outward to common logic; «extend» is optional and points inward from the extension back to the base case.

15. Component Diagram vs. Deployment Diagram

PYQ: [2022-23], [2025-26]
Criterion Component Diagram Deployment Diagram
Architectural View Implementation View: Structural organization, packaging, and dependencies of software modules. Deployment / Physical View: Physical topology of hardware nodes and allocation of software artifacts.
Core UML Artifacts Components (rectangles with tabs/icons), Provided Interfaces (lollipop), Required Interfaces (socket). Nodes (3D cubes representing physical servers/devices), Artifacts (manifestations), Communication Paths.
Focus Question "How is the software constructed and packaged into modular binary units?" "Where are software executables and databases physically hosted and run across the network?"
Key Connectors Interface delegation, assembly connectors, dependency vectors. Communication paths with protocols («TCP/IP», «HTTPS», «gRPC»).

Exam Takeaway: Component diagrams model software binaries and modular interfaces; Deployment diagrams model hardware nodes, devices, and physical network topologies.

Category IV: Design Methodologies, Analysis & Quality (Unit 3)

16. SA/SD vs. JSD vs. OMT (Comprehensive Methodological Benchmark)

PYQ: [2020-21], [2022-23], [2024-25], [2025-26]
Dimension SA/SD (Structured) JSD (Jackson Structured Dev.) OMT (Object Modeling Technique)
Originators Yourdon, DeMarco, Constantine Michael A. Jackson James Rumbaugh et al.
Decomposition Style Top-down functional decomposition into subroutines. Entity-centric modeling followed by concurrent process networks. Orthogonal tripartite modeling (Object, Dynamic, Functional).
Core Modeling Tools DFD, Data Dictionary, Structure Chart. Entity Structure Diagrams (ESD), System Specification (SSD). Class Diagrams, Statecharts, Functional DFDs.
Temporal Sequencing Weak: DFDs have zero time semantics or synchronization. Very Strong: Time ordering of entity event histories is paramount. Strong: Statecharts and interaction diagrams explicitly track time.
Data-Function Coupling Completely decoupled; passive data flows through active bubbles. Partially coupled; actions belong to entities, state vectors separated. Fully Unified: Encapsulated within class boundaries.
Concurrency Modeling Poor; assumes single-threaded sequential call-return trees. Exceptional: Built from day one as networks of concurrent processes. Strong; modeled natively via active objects and concurrent statecharts.
Semantic Gap Large; DFDs look completely different from Structure Charts. Moderate; requires state vector inversion to map onto code. Minimal: Seamless mapping from analysis classes to code classes.
Primary Application Batch pipelines, data processing, compilers. Real-time control systems, telecom switching. Enterprise software, GUI applications, distributed architectures.

Exam Takeaway: SA/SD focuses on functions and data flows; JSD focuses on time-ordered entity event histories; OMT unifies objects, states, and functions into a 3-model framework.

17. System Design (Macro-Level) vs. Object Design (Micro-Level)

PYQ: [2020-21], [2024-25]
Criterion System Design (Macro-Architecture) Object Design (Micro-Architecture)
Architectural Scope Global, strategic system-wide infrastructure and high-level structure. Detailed, internal class-level algorithmic and data structure specification.
Core Focus Areas Subsystem decomposition, hardware-software allocation, concurrency, data stores, security. Algorithm selection, concrete data structures, access visibility, method signatures.
Decomposition Technique Partitioning into horizontal architectural layers or vertical domain slices. Refining class definitions, optimizing associations, adjusting inheritance hierarchies.
Hardware Awareness High; explicitly maps software tiers to physical server nodes and cloud topologies. Low; operates within memory address spaces, abstract algorithms, and compilers.

Exam Takeaway: System Design is macro-architecture (tiers, concurrency, databases); Object Design is micro-architecture (classes, algorithms, visibility, optimizations).

18. The Three Models in Rumbaugh's OMT (Object vs. Dynamic vs. Functional)

PYQ: [2023-24], [2024-25]
Dimension 1. Object Model 2. Dynamic Model 3. Functional Model
Core Question "WHAT" is being modeled? "WHEN" does it happen? "HOW" is data computed?
Nature Static structural framework. Temporal reactive behavior. Computational transformation.
Primary Diagrams UML Class & Object Diagrams. Statechart & Sequence Diagrams. Data Flow Diagrams (DFDs) & Equations.
Core Concepts Classes, attributes, operations, associations. States, events, transitions, guards, actions. Processes, data stores, data flows, actors.
Role in System Provides the foundational memory structures. Controls sequencing and triggers operations. Specifies the algorithmic method bodies.

Exam Takeaway: Object Model provides the data skeleton; Dynamic Model controls the timing and triggers; Functional Model specifies the computational logic.

19. Transform Analysis vs. Transaction Analysis (Structure Charts)

Syllabus Core Topic
Criterion Transform Analysis Transaction Analysis
Data Flow Pattern Linear pipeline: input flow → central transformation → output flow. Radial star: a single input transaction tag triggers one of many branching paths.
Structure Chart Shape Balanced 3-branch structure: Afferent (input), Central Transform, Efferent (output). Shallow, wide fan-out structure: Transaction Center router controlling action modules.
Control Logic Sequential execution where outputs of one stage feed as inputs into the next. Conditional branching (switch/case) selecting exactly one execution path.
Typical Domain Mathematical calculations, signal processing, compilers, batch payroll engines. ATM transaction dispatchers, menu navigation routers, online shopping carts.

Exam Takeaway: Transform Analysis maps linear pipelines (Input → Process → Output); Transaction Analysis maps branching routers driven by a transaction tag.

20. Inheritance vs. Delegation (Composition over Inheritance)

PYQ: [2022-23]
Criterion Inheritance (White-Box Reuse) Delegation / Composition (Black-Box Reuse)
Relationship Type "is-a" taxonomic subtyping relationship. "has-a" object containment and message forwarding relationship.
Coupling Level Tight: Subclass is tightly bound to the internal implementation details of superclass. Loose: Host class interacts with delegate purely through its public abstract interface.
Binding Time Static compile-time binding; behavior cannot be swapped dynamically at runtime. Dynamic runtime binding; delegate instances can be swapped on the fly (Strategy pattern).
Encapsulation Impact Weakens encapsulation (subclasses often expose superclass protected state). Preserves strict encapsulation (delegate internals remain private).
Design Principle Use strictly when Liskov Substitution Principle (LSP) holds true unconditionally. "Favor object composition over class inheritance" (Gang of Four guideline).

Exam Takeaway: Inheritance provides static white-box reuse (tight coupling); Delegation provides dynamic black-box reuse (loose coupling, preferred by modern design).

21. High Cohesion vs. Low Coupling

PYQ: [2022-23]
Criterion Cohesion (Internal Module Focus) Coupling (Inter-Module Interdependence)
Architectural Scope Intra-module metric: Measures how strongly related and focused the internal responsibilities of a single module are. Inter-module metric: Measures the degree of direct interdependence between separate software modules.
Ideal Architectural Goal MAXIMIZE (High Cohesion): Every class should have a single, well-defined domain responsibility (Single Responsibility Principle). MINIMIZE (Low Coupling): Modules should communicate through abstract interfaces with zero awareness of external internals.
Spectrum from Worst to Best Coincidental → Logical → Temporal → Procedural → Communicational → Sequential → Functional (Best). Content → Common → Control → Stamp → Data (Best) → Message (No Direct Coupling, Best).
Impact on Maintenance High cohesion ensures classes are easy to understand, test, debug, and reuse. Low coupling ensures changes in one module do not cause unexpected cascading errors in other modules.

Exam Takeaway: Golden rule of software engineering: Strive for High Cohesion (focused internals) and Low Coupling (independent modules).
